# 具体测试流程

> 说明这一轮优化（硬解、低延迟追帧、断线重连、丢包不花屏、看门狗、音频衔接、运行指标）是怎么测的：测试环境、测试源、故障怎么注入、结果怎么判定，以及怎么复现。
> 自动化测试集的用法速查见 [live/README.md](live/README.md)；各项优化的原理见 [docs/优化记录.md](../docs/优化记录.md)。

## 1. 测试思路

真实的摄像头和网络不可控、不可重复，所以全部改成**在本机搭一条可控的直播链路**：

```
FFmpeg 推流端 ──UDP/TCP──► [网络模拟器 netem_relay.py] ──► 播放器 SimpleFFPlay6_0 -lowlatency
 (lavfi 合成画面 + 正弦音)      丢包 / 抖动 / 乱序 / 卡顿            -stats 状态行、日志、指标文件、导出的音频 PCM
```

- **推流端**：FFmpeg 实时生成测试画面和 440Hz 正弦音，编码后推出去，可以随时停掉 / 重启来模拟摄像头掉线。
- **网络模拟器**：夹在中间转发 UDP 包，按参数制造丢包、抖动、乱序、卡顿后突发。
- **播放器**：带 `-stats` 打印实时状态，带 `-metrics_file` 写指标；测试用环境变量还能让它模拟解码器卡死、导出实际播放的声音。
- **判定**：脚本解析播放器的输出，按事先定好的标准判 PASS / FAIL，而不是靠肉眼看。

## 5. 自动化测试集：11 个场景

运行：

```bash
python3 -I tests/live/run_live_tests.py                      # 全部，约 4 分钟
python3 -I tests/live/run_live_tests.py --only clean,stall_6s
python3 -I tests/live/run_live_tests.py --nohwaccel          # 播放器用软解
```

### 5.1 每个场景的执行步骤

1. 选两个不冲突的本地端口；UDP 场景先启动网络模拟器（`in_port → out_port`）。
2. 启动推流端（UDP 场景推到模拟器；TCP 场景推流端以 `listen=1` 监听，播放器去连它）。
3. 0.5 秒后启动播放器：`-lowlatency -stats -loglevel warning -metrics_file <场景>.metrics.jsonl -metrics_interval 1`，UDP 场景再加 `SIMPLEFFPLAY_TEST_AUDIO_DUMP`。
4. 后台线程读播放器的 stderr，按 `\r` / `\n` 切分，每一段打上"距播放器启动的秒数"，写进 `<场景>.log`。
5. 按场景的时间表操作推流端（例如第 7 秒停、第 11 秒重启）。
6. 到时间后 SIGTERM 结束播放器（会自行退出的场景则等它退出，并记录退出时刻）；结束推流端和模拟器，收集模拟器的统计。
7. 解析与判定（§6），把结果写进 `report.json`。

### 5.2 场景表

| 场景 | 传输 | 注入的故障 | 主要验证 |
|---|---|---|---|
| `clean` | UDP | 无 | 稳态延迟；没有误判（冻结、跳关键帧、断线都应为 0）；声音无咔哒无断口 |
| `jitter_80ms` | UDP | 每包随机延迟 0~80ms | 目标延迟能自动升高；只有抖动不能被误判为损坏 |
| `blackout_300` | UDP | 第 8 秒起丢光 300ms | 丢包不花屏：冻结一次，下一个关键帧恢复 |
| `loss_1pct` | UDP | 1% 随机丢包 | 每次冻结都能恢复，不会永久卡死 |
| `reorder` | UDP | 0~20ms 抖动 + 1% 乱序 | 同上 |
| `stall_1500` | UDP | 第 8 秒起扣住 1.5 秒后突发放出 | 卡顿后追帧，延迟回落 |
| `stall_6s` | UDP | 第 6 秒起扣住 6 秒 | 4 秒读超时 → 判定断线 → 重连 → 追回 |
| `decoder_hang` | UDP | 第 8 秒让解码线程卡住 | 看门狗第 1 级无效、第 2 级重建解码器后恢复，不升级到重连 |
| `tcp_restart` | TCP | 推流端第 7 秒停、第 11 秒重启 | 断线重连：0/1/2/3 秒重试后连上 |
| `tcp_give_up` | TCP | 推流端第 7 秒停、不再恢复 | 重试 0/1/2/3/4/5 秒后放弃，约 22.5 秒自行退出，写出指标汇总 |
| `tcp_late` | TCP | 推流端第 3 秒才启动 | 首次连接失败后重试连上 |

## 6. 怎么判定

### 6.1 数据来源

| 来源 | 内容 |
|---|---|
| `-stats` 状态行 | `lag`（当前画面比最顺利情况晚多少）、`tgt`（目标延迟）、`jump`、`frz`、`wd`、`au`/`aw`/`ad` |
| 日志事件（`live:` 开头） | 冻结 / 恢复及时长、跳关键帧、断线 / 重连 / 放弃、看门狗级别、音频滞后提示 |
| 指标文件 | 每秒一行 JSON（fps、延迟分位、冻结时长、重连次数……） |
| 导出的 PCM | 用于咔哒和断口检测 |

### 6.2 各类检查

| 检查 | 方法 | 标准 |
|---|---|---|
| 稳态延迟 | 取最后 6 秒的 `lag`，算 p95 | `clean` ≤ 150ms |
| 抖动下延迟 | 同上 | `jitter_80ms` ≤ 300ms（需求上限） |
| 卡顿后追回 | 最后 5 秒 `lag` p95 + 最后一个 `lag` | p95 ≤ 300ms 且最终 ≤ 150ms |
| 丢包不花屏 | 数"冻结 / 恢复"事件，读每次冻结时长 | 有冻结、每次都恢复（最后一次可在进行中）；`blackout_300` 单次 ≤ 1.5 秒、占比 ≤ 15%；随机丢包单次 ≤ 8 秒、占比 ≤ 60%；不能触发 10 秒保护超时 |
| 重连 | 读断线、重连事件及时刻 | 检测到断线并重连；`tcp_give_up` 在 20~28 秒内自行退出 |
| 看门狗 | 读看门狗级别序列 | `decoder_hang` 前两级是 [1, 2]，不能出现 3 |
| 不误判 | 统计不该出现的事件 | `clean` 无冻结 / 跳转 / 断线；`jitter_80ms` 无冻结 |
| 指标一致 | 读指标文件最后一行 | `tcp_restart` 重连 = 1；`blackout_300` 冻结 = 1 且 0~2 秒；`decoder_hang` 看门狗 ≥ 2；`tcp_give_up` 有汇总行；`clean` 帧率 20~30 |
| 声音 | 见 6.3 | `clean`、`jitter_80ms` 咔哒 0 次；其余 UDP 场景 ≤ 1 次；`clean` 断口 ≤ 2 |

### 6.3 咔哒声怎么"测"出来

听感没法自动判断，所以用纯正弦波做测试音：

- 幅度为 A、频率 f 的正弦，相邻两个采样点之差最大是 `2π·f/fs·A`（440Hz、48kHz、A≈4100 时约 236）。
- 输出 PCM 里如果相邻采样点之差超过这个理论上限的 **2.5 倍**，就是波形断了，也就是一次咔哒；10ms 内的多次跳变算一次。
- 幅度 A 取全部采样绝对值的 99.9 分位，避免被个别尖峰带偏；开头播放前的静音、前 3 秒跳过。
- **静音断口**：开始出声后出现 ≥ 1ms 的连续全零段。

## 7. 自动化测试集之外做过的测试

| 测试 | 怎么做 | 结论 |
|---|---|---|
| 硬解 / 软解切换 | 用 `h264_videotoolbox`、`hevc_videotoolbox`、`mpeg4` 编出三个文件，分别播放看日志 | H.264、HEVC 走 VideoToolbox；MPEG-4 硬解初始化失败后自动退回软解 |
| 普通文件回归 | 每轮改动后 `-autoexit` 播放本地文件，看退出码和错误输出 | 退出码 0、无错误输出（不开 `-lowlatency` 时行为不变） |
| 偶发卡住排查 | 一次纯视频文件播完没退出，用改动前后三个版本、多种参数重复 26 次 | 无法复现，判断与本轮改动无关 |
| 音频 A/B | `audio_ab.sh` 开 / 关 `-audio_smooth`，干净 / 卡顿 / 丢包各跑一次 | 咔哒 182/169/136 次 → 0 |
| 音频断口定位 | 把 `au/aw/ad` 加进 `-stats`，再临时打点每次丢帧时音频落后多少 | 发现音频成批晚到约 200ms；推流端加 `-pes_payload_size 0`（每帧单独打包）后断口消失，证实原因 |
| 首次连接 | 播放器先启动、推流端晚上线 / 不上线 / 地址写错 | 自动连上 / 约 15 秒放弃 / 0.5 秒直接退出 |

## 8. 测试中发现并修掉的问题

自动化测试比"跑一下看看"多抓到了这些问题：

| 问题 | 怎么发现的 |
|---|---|
| UDP 重连永远失败（旧连接占着端口） | `stall_6s` 前身：日志里每次重连都 `Address already in use` |
| 重连后要多等 5 秒才出画面 | 重连日志时间戳：连上到恢复播放间隔 5.4 秒 → 探测时长降到 1 秒后 1.6 秒 |
| 冻结期间误触发跳关键帧、清掉音频 | `loss_1pct`：`jump` 计数在没有积压时上涨 |
| 起播阶段的坏帧被算成冻结 | `clean`：无故障却报 1 次冻结 |
| 卡顿后目标延迟顶在上限 5 秒 | `decoder_hang`：最后 5 秒 p95 323ms 超标 → 加 ±3.5σ 限幅 |
| 连续播放的音频被反复插静音 | `audio_ab.sh`：干净网络也有约 7 段/秒断口 |
| 音频成批晚到被反复丢帧 | `-stats` 的 `ad` 每秒涨约 30 |
| 主线程卡住时看门狗误判 | `jitter_80ms`：指标文件出现 3.9 秒空档、看门狗触发 |
| 重连后 / UDP 卡顿恢复时看门狗误判 | `tcp_restart`、`stall_6s` 的指标文件 `watchdog=1` |

## 9. 最近一次结果（2026-11-23，硬解）

11/11 通过：

| 场景 | 关键数据 |
|---|---|
| `clean` | lag p95 64ms，帧率 25，咔哒 0、断口 0 |
| `jitter_80ms` | 目标延迟约 95ms，lag p95 137ms，无冻结，咔哒 0、断口 0 |
| `blackout_300` | 冻结 1 次 37ms |
| `loss_1pct` | 冻结 5 次，全部恢复 |
| `reorder` | 冻结 2 次，全部恢复 |
| `stall_1500` | 卡顿后 lag p95 64ms |
| `stall_6s` | 重连 1 次（断线约 2 秒），lag p95 65ms，看门狗 0 |
| `decoder_hang` | 看门狗第 1、2 级，恢复后 lag p95 64ms |
| `tcp_restart` | 重连 1 次（断线约 7.7 秒），看门狗 0 |
| `tcp_give_up` | 约 22.2 秒放弃退出，写出汇总 |
| `tcp_late` | 约 4.6 秒连上 |

`--nohwaccel` 下最近一次跑的是 11-19 版本的损坏相关场景（`blackout_300`、`loss_1pct`、`reorder`），全部通过；之后的改动没有重跑软解。

## 10. 这套测试测不到的

- **端到端延迟**：`lag` 不含摄像头编码和网络最低传输时间。真实值要用摄像头对着秒表拍、再拍屏幕对比。
- **真实摄像头 / 真实网络**：全是本机回环 + 合成流；Wi-Fi 抖动、摄像头自身的怪异行为没测过。
- **RTSP over UDP 丢包**：需要一个 RTSP 服务端（如 mediamtx）才能测。
- **长时间稳定性**：每个场景只跑 12~35 秒，内存泄漏、句柄泄漏、长时间运行后的时间戳回绕都测不到（计划中的 12~24 小时挂机测试已暂缓）。
- **多路同屏性能**：只测了单路。
- **GUI 相关**：测试会接连弹出多个窗口，窗口遮挡可能导致主线程卡顿（测试中出现过一次 3.9 秒），这类问题有偶发性。
