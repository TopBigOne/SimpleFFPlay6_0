## P0：真实摄像头端到端延迟实测（最有价值）

**为什么**：目前所有数据都来自本机回环 + 合成测试流。播放器打印的 `lag` 只是"比最顺利的包晚多少"，不含摄像头编码和网络最低传输时间——**300ms 的目标到底有没有达到，只能用真实摄像头测出来。**

**需要**：一台支持 RTSP 的摄像头（局域网内）、一部能显示毫秒的秒表（手机秒表 App 或网页秒表）、另一部手机用来拍照。

**步骤**：
- [ ] 摄像头设置：关闭 B 帧（或选 Baseline / Main profile 且 GOP 内无 B 帧），关键帧间隔 1~2 秒，记录分辨率、帧率、码率。
- [ ] 播放：
      ```bash
      ./SimpleFFPlay6_0 -lowlatency -rtsp_transport tcp -stats -metrics_file cam.jsonl rtsp://<摄像头地址>
      ```
- [ ] 让摄像头对着秒表，播放器窗口和秒表并排放；用另一部手机同时拍下两者，**照片里两个读数之差就是端到端延迟**。拍 10 张以上，取中位数和最大值。
- [ ] 同时记录 `-stats` 里的 `lag` / `tgt`，对比"端到端延迟 − lag"，得到摄像头编码 + 网络固定延迟的量级。
- [ ] 对照组：同一摄像头用不带 `-lowlatency` 的原版模式各拍一组，量化改进幅度。
- [ ] 可选：`-rtsp_transport udp` 再测一组；用摄像头自带的客户端或 VLC 测一组做横向对比。
- [ ] 稳定性抽查：播放中拔网线 10 秒再插回、重启摄像头，确认能自动恢复；看指标文件里的 `reconnects`、`disconnected_ms`。

**验收**：端到端延迟中位数 ≤ 300ms；把结果（含照片样例、摄像头型号与参数、`cam.jsonl` 汇总）写进 `tests/具体测试流程.md` 新增的"真实摄像头"一节，并更新 `优化记录.md`。

**如果超标**：先看 `lag` 是否接近目标延迟（30~100ms）。如果 `lag` 很小而端到端很大，瓶颈在摄像头编码或网络，播放器侧再优化意义不大；如果 `lag` 大，看 `-stats` 的 `jump` / `frz` / `wd` 和指标文件定位。
