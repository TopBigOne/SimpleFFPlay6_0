# SimpleFFPlay6.0 优化记录

> 范围：从首次提交 `6039d74` 起的全部改动（2026-11-19 ~ 2026-11-23）。第 10~11 项及音频断音修复是 2026-11-23 补做的。
> 目标场景：**家庭安防监控直播**，端到端延迟 300ms 以内，稳定性与可靠性向 WebRTC 接收端对齐。
> 所有直播相关能力都挂在 `-lowlatency` 开关下，默认关闭，不影响普通文件播放。

## 1. VideoToolbox 硬解（`94a320e`）

**问题**：原版只做软解，没有任何硬解代码。

**做法**：
- 打开视频流时，如果解码器支持 VideoToolbox，就创建硬件设备挂到解码器上（[stream.c](../src/demux/stream.c) `setup_videotoolbox()`）。
- 硬解初始化失败（例如不支持的 profile）时，`get_format` 回调自动退回软件格式。
- 硬解出的帧拷回内存（[decoder.c](../src/pipeline/decoder.c)），后续的滤镜和渲染流程不用改。
- 默认开启，`-nohwaccel` 关闭；开了 `-lowres` 时不走硬解。

**验证**：H.264、HEVC 走硬解；MPEG-4 Part 2 硬解初始化失败后自动退回软解，播放正常。

**遗留**：硬解帧要先拷回内存，再做一次 NV12 → YUV420P 转换，多路同屏时会成为 CPU 瓶颈。

## 2. 低延迟直播模式：追帧（`94a320e`）

**问题**（原版 ffplay）：
- 包队列固定攒约 1 秒才停读，稳态延迟就有 1 秒；
- 以音频为主时钟、1.0 倍速播放，卡顿造成的延迟永远追不回来；
- 唯一的调速机制（外部时钟最快 1.01 倍）只对 RTP/RTSP/UDP 生效，而 RTMP、HTTP-FLV、HLS 都不算。

**做法**（借鉴 WebRTC 视频接收端，详见 [live_catchup_algorithm.md](live_catchup_algorithm.md)）：

| 环节 | 做法 | 位置 |
|---|---|---|
| 测延迟 | 基准 = 最近 2 秒内"到达时间 − pts"的最小值，不需要摄像头墙钟 | [live_latency.c](../src/live/live_latency.c) |
| 目标延迟 | 抖动均值 + 2.33σ + 5ms，变大立刻生效，变小每秒最多降 100ms，限制在 30~300ms | 同上 |
| 显示 | 每帧在 `pts + 基准 + 目标延迟` 时显示；后一帧也到时刻了就丢掉当前帧 | [video_refresh.c](../src/video/video_refresh.c) |
| 积压兜底 | 关键帧到达时，若比当前画面超前 600ms 以上，清空队列从它开始 | [read_thread.c](../src/demux/read_thread.c) `live_on_packet()` |
| 音画同步 | 视频为主时钟；音频落后 80ms 以上就丢，开始出声时等到截止时刻 | [audio_output.c](../src/audio/audio_output.c) |
| 其他 | 读线程不停读；声卡缓冲约 46ms → 11ms；探测流信息最多 1 秒（原 5 秒）；解码器开 `LOW_DELAY` | — |

**效果**（本机回环、合成流）：

| 场景 | 结果 |
|---|---|
| 稳态 | 额外延迟中位数约 50~70ms，p95 约 65~90ms |
| 卡顿 1.5 秒 | 跳一次关键帧，约 3 秒回到稳态 |
| 80ms 网络抖动 | 目标延迟自动升到约 89ms，p95 约 135ms |
| 音画同步 | 误差在 ±10ms 以内 |

**注意**：`lag` 是"比最顺利的包晚了多少"，不含摄像头编码和网络最低传输时间；摄像头需关闭 B 帧。

## 3. 断线重连 / 首次连接重试（`7880533`、`566277e`）

**问题**：原版遇到网络错误时读线程直接退出，画面冻结且不会恢复；摄像头不在线时直接报错退出。

**做法**（重试规则照搬 ExoPlayer `DefaultLoadErrorHandlingPolicy`）：
- 读包遇到 EOF、IO 错误，或 **4 秒读不到数据**（中断回调超时），判定为断线。
- 重试等待 `min((n−1) × 1s, 5s)`，即 0、1、2、3、4、5 秒；**连续 6 次一个包都没读到**才放弃，读到包就清零。
- 解析错误、文件不存在、协议不支持、选项写错，直接放弃不重试。
- 先建好新连接再替换旧连接；替换后重建解码器，延迟估计重置；用户原来的打开参数（如 `-rtsp_transport tcp`）保留。
- 首次连接失败也按同样规则重试。
- 选项：`-live_reconnect`（默认跟随 `-lowlatency`）、`-reconnect_max`（默认 6，0 = 无限）。

**开发中修掉的问题**：UDP 重连时旧连接占着本地端口，新连接报 `Address already in use`——判定断线后先释放旧连接的网络资源。

**效果**：

| 场景 | 结果 |
|---|---|
| TCP 推流端停 4 秒后恢复 | 第 4 次重试连上，约 1.6 秒恢复播放 |
| 推流端一直不恢复 | 约 22.5 秒放弃并退出 |
| UDP 中断 6 秒 | 4 秒超时后重连，数据恢复后追回延迟 |
| 摄像头晚 3 秒上线 | 自动连上 |

## 4. 丢包不花屏（`a534b6d`）

**问题**：丢包后，后续 P 帧都参考了坏数据，会持续花屏直到下一个关键帧。

**做法**（WebRTC 规则：参考链不完整的帧不显示）：
- FFmpeg 6.0 不会把包上的"损坏"标记（如 MPEG-TS 连续计数器断了）传到帧上，在 [decoder.c](../src/pipeline/decoder.c) 里自己补上；解码器拒收数据时同样标记。
- 出现损坏帧后，丢弃后续所有帧，画面停在最后一个好帧，直到干净的关键帧（[video_decoder_thread.c](../src/video/video_decoder_thread.c) `frame_integrity_ok()`）。
- 冻结期间不触发"积压跳关键帧"；10 秒没等到关键帧（逐行刷新的摄像头）就放弃等待。
- 选项 `-freeze_on_corrupt`，默认跟随 `-lowlatency`；`-stats` 显示 `frz=`。

**效果与结论**：
- 连续丢包 300ms：冻结约 0.76 秒，在下一个关键帧恢复。
- **1% 随机丢包会冻结约一半时间**（一个关键帧约 40 个 UDP 包，被打坏的概率约三分之一）。没有重传时这是"不花屏"的代价，因此 **RTSP 应使用 `-rtsp_transport tcp`**（TCP 重传相当于 WebRTC 的 NACK）。
- 硬解只能依赖传输层的损坏标记，检测不如软解全面（同样 1% 丢包，软解 14 次冻结、硬解 5 次）。

## 5. 看门狗（`ff4d4ee`）

**问题**：网络正常、数据一直在到，但画面不动（解码器卡死、硬解异常），播放器不会自己恢复。

**做法**（对应 WebRTC 等不到可解码帧超时后的处理）：
- 条件：有视频、未暂停、出过画面、不在损坏冻结中、1 秒内有视频包，但 **3 秒没有显示新画面**。
- 逐级恢复，每级之间再等 3 秒：① 清空队列 → ② 重建视频解码器 → ③ 断开重连。
- 正常播放 10 秒后级别清零；`-stats` 显示 `wd=`。

**效果**：模拟解码器卡死后，13.7 秒触发第 1 级（无效），16.7 秒第 2 级重建解码器，画面恢复，未升级到重连。

**局限**：如果线程真的卡死在 libavcodec 内部，关闭解码器时会一直等它退出，读线程也会被卡住。

**后续（2026-11-23）修掉的误判**：主线程被阻塞（疑似 macOS 窗口遮挡）时帧队列是满的，不再动作；重连成功时重置计时；要求上次出画面以来至少收到 40 个视频包。

## 6. 抖动估计限幅（`ff4d4ee`）

**问题**：单个几秒的异常值（卡顿后、解码器重建后的第一批帧）会把方差推高，目标延迟在 300ms 上限停留约 5 秒。

**做法**：每帧相对均值的偏差限制在 ±3.5σ（σ 至少按 5ms 算），前 30 帧不限幅（起播阶段要快速收敛）。对应 WebRTC `jitter_estimator.cc` 的离群处理。

**效果**：

| 场景 | 卡顿后最后 5 秒延迟 p95（改前 → 改后） |
|---|---|
| 卡顿 1.5 秒 | 127ms → 64ms |
| 解码器卡死 | 323ms → 64ms |
| 80ms 抖动 | 目标延迟仍能升到约 88ms，不受影响 |

## 7. 音频衔接（`ff4d4ee`）

**问题**：断音、丢帧、跳转时波形突然跳变，产生"咔哒"爆音。

**做法**（WebRTC NetEq Expand / Merge 的简化版，[audio_smooth.c](../src/live/audio_smooth.c)）：
- 一直记住最后输出的 5ms。
- 没数据要转静音时，先播 5ms 由尾巴"镜像延续"并渐弱到 0 的声音（镜像保证接缝处连续）。
- 从静音恢复、丢过帧、时间戳跳变时，新数据开头 5ms 与尾巴镜像交叉淡化。
- 选项 `-audio_smooth`，默认跟随 `-lowlatency`。

**同时修正的问题**：第 2 项的"音频等到截止时刻再出声"原来对每一帧都检查，目标延迟的小幅波动让连续播放的音频被反复插入静音。改为只在开始出声（起播、断音后、接不上时）才对齐。

**效果**（440Hz 正弦测试源，统计输出 PCM 中的波形跳变）：

| 场景 | 咔哒（关 → 开） | 静音断口 |
|---|---|---|
| 干净网络 | 约 13 次/秒 → 0 | 约 7 段/秒 → 约 2.4 段/秒 |
| 卡顿 1.5 秒 | 169 → 0 | — |
| 1% 丢包 | 136 → 0 | — |

**后续（2026-11-23）**：剩余的约 2.4 段/秒静音断口已查清并解决——测试源把多个 AAC 帧攒成一个 MPEG-TS 包发出，音频比视频晚到约 200ms，被反复"丢掉 → 重等 → 插静音"。改为接受稳定的音频滞后（最多 0.5 秒）连续播放后，断口降为 0，代价是这类源音画差约 200ms。详见 [live_reliability.md](live_reliability.md) §3.3。

**已知遗留**：故障恢复瞬间偶发 1 次咔哒（采样补偿 / 解码器 flush），见 [live_reliability.md](live_reliability.md) §3.5。

## 7.1 运行指标（2026-11-23）

`-metrics_file <路径>` / `-metrics_interval <秒>`（默认 5）：每个间隔写一行 JSON，正常退出时写汇总，对应 WebRTC getStats。字段：帧率、码率、延迟 p50/p95/p99、丢帧、冻结次数与总时长、跳关键帧、重连次数与断线总时长、看门狗、音频断音 / 等待 / 丢帧 / 接受的滞后。实现 [live_metrics.c](../src/live/live_metrics.c)，字段说明见 [live_reliability.md](live_reliability.md) §4。测试集每个场景都校验指标与日志一致。

## 新增命令行选项汇总

| 选项 | 默认 | 作用 |
|---|---|---|
| `-hwaccel` / `-nohwaccel` | 开 | VideoToolbox 硬解 |
| `-lowlatency` | 关 | 低延迟直播模式总开关 |
| `-latency_min` / `-latency_max` | 30 / 300（ms） | 目标延迟范围；积压超过上限 2 倍跳关键帧 |
| `-live_reconnect` | 跟随 `-lowlatency` | 断线重连与首次连接重试 |
| `-reconnect_max` | 6 | 连续无进展的最大重试次数，0 = 无限 |
| `-freeze_on_corrupt` | 跟随 `-lowlatency` | 丢包不花屏 |
| `-audio_smooth` | 跟随 `-lowlatency` | 音频衔接 |
| `-metrics_file` / `-metrics_interval` | 不输出 / 5 秒 | 运行指标 |

`-stats` 状态行在低延迟模式下新增：`lag`（当前画面额外延迟）、`tgt`（目标延迟）、`jump`（跳关键帧次数）、`frz`（损坏冻结次数）、`wd`（看门狗触发次数）、`au`/`aw`/`ad`（音频断音 / 等待 / 丢帧）。
