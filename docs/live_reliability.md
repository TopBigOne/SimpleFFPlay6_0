# 直播可靠性：看门狗、音频衔接、运行指标

> 本文是 [live_catchup_algorithm.md](live_catchup_algorithm.md)（追帧、重连、丢包不花屏）的续篇，描述 `-lowlatency` 模式下另外三项可靠性机制。
> 测试方法与结果见 [tests/live/README.md](../tests/live/README.md)；所有数据来自本机回环 + 合成测试流。

## 1. 看门狗（卡死自动恢复）

**解决的问题**：网络正常、数据一直在到，画面却不动了（解码器卡死、硬解异常）。追帧、重连都管不到这种情况。

**实现**：[read_thread.c](../src/demux/read_thread.c) `watchdog_check()`，读线程每轮循环调用一次。

### 1.1 判定条件（全部满足才算卡死）

| 条件 | 为什么 |
|---|---|
| 低延迟模式、有视频、没暂停、不在逐帧步进 | 只管直播播放中的情况 |
| 已经出过画面 | 起播阶段由连接 / 重试逻辑负责 |
| 不在"损坏冻结等关键帧"中 | 那是有意冻结，有自己的 10 秒上限 |
| 最近 1 秒有视频包，且**上次出画面以来收到 ≥ 40 个视频包** | 确认数据真的一直在到。网络卡住后数据刚恢复的那一刻，"有包 + 很久没画面"会同时成立，只看最近 1 秒会误判 |
| **帧队列不是满的** | 队列满说明解码器在正常产出，是显示端没取帧（例如 macOS 窗口被遮挡时画面提交阻塞），清队列、重建解码器都没用 |
| **3 秒没有显示新画面** | 同 WebRTC `kMaxWaitForFrame = 3s` |

### 1.2 逐级恢复

每级动作之后再等 3 秒看效果，没好转才升级：

| 级别 | 动作 | 能解决 |
|---|---|---|
| 1 | 清空三个包队列（serial + 1，解码器 flush，从下一个关键帧重来） | 解码器状态错乱、积压 |
| 2 | 关闭并重建视频解码器（abort 包队列、等解码线程退出、重新打开） | 解码线程卡住 |
| 3 | 断开重连（复用 `handle_disconnect()`） | 连接层异常 |

画面恢复正常 10 秒后级别清零；连接 / 重连成功时也会重置看门狗计时，避免把"重连期间没画面"误判成卡死。`-stats` 显示 `wd=` 累计触发次数。

### 1.3 验证

测试场景 `decoder_hang`：环境变量 `SIMPLEFFPLAY_TEST_STALL_DECODER_AT=8` 让视频解码线程在第 8 秒卡住，只有被关闭时才退出（和真实卡死一样，清队列救不回来）。

结果：卡住后约 3 秒触发第 1 级（无效），再 3 秒第 2 级重建解码器，画面恢复，没有升级到重连；恢复后最后 5 秒 lag p95 64ms。

开发中修掉的误判：
- 主线程被阻塞约 4 秒（疑似 macOS 窗口遮挡）时，第一版看门狗误以为解码器卡死 → 加了"帧队列满则不动作"。
- 重连 / UDP 卡顿恢复后数据一到就触发 → 加了"重连时重置计时"和"至少 40 个包"。

### 1.4 局限

如果线程真的卡死在 libavcodec 内部（而不是测试钩子里那样可以被 abort 唤醒），第 2 级关闭解码器时会一直等它退出，读线程也会被卡住。这种情况进程内无法恢复，需要外部守护进程重启播放器。

## 2. 抖动估计限幅

**问题**：单个几秒的异常值（卡顿后、解码器重建后的第一批帧）会把方差推高，目标延迟在 300ms 上限停留约 5 秒。

**做法**：[live_latency.c](../src/live/live_latency.c) `live_latency_on_frame()`，每帧相对均值的偏差限制在 ±3.5σ（σ 至少按 5ms 算）；前 30 帧不限幅，因为起播阶段探测期攒下的包会一次性交出，均值要能快速收敛。对应 WebRTC `jitter_estimator.cc` 的离群处理。

| 场景 | 卡顿后最后 5 秒 lag p95（改前 → 改后） |
|---|---|
| `stall_1500` | 127ms → 64ms |
| `decoder_hang` | 323ms → 64ms |
| `jitter_80ms` | 目标延迟仍能升到约 88~96ms，不受影响 |

## 3. 音频衔接与音画滞后

### 3.1 消除咔哒声（`-audio_smooth`）

**问题**：断音、丢帧、跳转时波形突然跳变，产生"咔哒"爆音。

**做法**（WebRTC NetEq Expand / Merge 的简化版，[audio_smooth.c](../src/live/audio_smooth.c)，只在 SDL 音频回调线程里使用）：

- 一直记住最后输出的 5ms（"尾巴"）。
- **有声 → 没数据**：先输出 5ms 由尾巴"镜像延续"并渐弱到 0 的声音，再输出静音。镜像（倒放尾巴）保证第一个样本就等于上一个输出样本，接缝处不会再跳一次。
- **新数据接不上**（从静音恢复、丢过帧、serial 变了、时间戳差 20ms 以上）：新数据开头 5ms 与尾巴镜像交叉淡化：
  `out[i] = new[i]·g + mirror[i]·(1 − g)`，`g` 从 0 线性升到 1。从静音恢复时尾巴为 0，交叉淡化就是淡入。
- 只处理衔接处的 5ms，不额外增加延迟。默认跟随 `-lowlatency`。

### 3.2 只在"开始出声"时对齐截止时间

追帧机制要求音频跟视频用同一个截止时间出声，否则音频会比画面超前约一个目标延迟。第一版对**每一帧**都检查"到没到时刻"，目标延迟和基准的小幅波动让连续播放的音频被反复判成"早了"而插入静音。

改为只在 `audio_running == 0`（起播、断音后、接不上时）才等截止时间；连续播放中绝不插静音，偏差交给 ffplay 原有的 ±10% 采样补偿慢慢修正（同 NetEq：靠变速而不是插静音）。

### 3.3 音频稳定晚到时接受滞后

**问题**：排查剩余断音时发现，测试源（FFmpeg 默认的 MPEG-TS 封装）把多个 AAC 帧攒成一个 PES 一起发，音频比同时刻的视频**晚到约 200~260ms**。每批到达时前几帧已经落后视频 80ms 以上被丢掉，然后重新等截止时间、插静音，循环往复，形成约每秒 2.4 段的断音。推流端改成每帧单独打包（`-pes_payload_size 0`）后断音完全消失，证实了这个原因。真实的 RTSP 摄像头每个 RTP 包带一个音频帧，一般没有这个问题；但 UDP 直推 / HLS 等 MPEG-TS 来源常见。

**做法**（[audio_output.c](../src/audio/audio_output.c) `audio_frame_too_late()`）：

- 音频落后视频超过 80ms、但不到 **0.5 秒**时，不丢，而是记下这个滞后（`audio_lag_accept`），之后以"晚这么多"为目标连续播放；`synchronize_audio()` 的同步目标同步放宽，否则采样补偿会把音频往前拉到断粮。
- 落后超过 0.5 秒才丢（那是卡顿后的积压，不是稳定滞后）。
- 音频追上视频后，每帧收回 1ms 滞后，源改善时音画自动重新对齐。
- 第一次出现时打印一条提示：`audio arrives ~XXXms later than video ...`。

取舍：**安防场景画面实时优先**——宁可音画差约 200ms，也不让画面跟着多等 200ms，更不让声音一段一段的。

### 3.4 效果

用 440Hz 正弦测试源，导出实际交给声卡的 PCM（`SIMPLEFFPLAY_TEST_AUDIO_DUMP`），统计波形跳变（相邻样本差超过正弦理论上限 2.5 倍）和静音断口（`tests/live/audio_clicks.py`）：

| 场景 | 咔哒 | 静音断口 |
|---|---|---|
| 干净网络，衔接关闭（旧逻辑） | 约 13 次/秒 | 约 7 段/秒 |
| 干净网络，衔接开启 + 3.2 + 3.3 | **0** | **0** |
| 每帧单独打包的音频 | 0 | 0~1（起播时） |
| 卡顿 / 丢包 / 乱序 / 重连 | 0（偶发 1 次，见下） | 0~1 |

音画差：每帧打包的源约 2ms；音频打包晚到的源按设计接受约 190~260ms。

### 3.5 已知遗留

故障恢复的瞬间偶发 1 次咔哒（不是每次运行都出现），两种形态：
- 连续正弦里跳过 2~3 个样本，像是 `synchronize_audio` 的采样补偿造成的；
- 跳关键帧时音频解码器被 flush，新解码器输出开头有一段比 5ms 窗口更长的衰减振荡。

彻底消除需要改动采样补偿方式（例如改用 `atempo` 做不变调变速）或延长 flush 后的淡入，暂未处理。测试集对干净 / 抖动场景要求 0 次，对故障恢复场景允许 1 次。

## 4. 运行指标（`-metrics_file`）

**对应**：WebRTC `getStats`。回答"这一路昨晚卡了几次、断了几次、延迟多少"。

**用法**：

```bash
./SimpleFFPlay6_0 -lowlatency -metrics_file cam1.jsonl -metrics_interval 5 rtsp://...
```

每 `-metrics_interval` 秒（默认 5）写一行 `{"type":"interval",...}`，正常退出时写一行 `{"type":"summary",...}`（覆盖全程）。被 SIGTERM 杀掉时 ffplay 直接退出，不会写汇总。

**示例**（重连场景的一行区间记录）：

```json
{"type":"interval","t":20.0,"fps":25.0,"kbps":1060,"lag_ms":{"p50":35,"p95":35,"p99":35},
 "frames_shown":411,"frames_dropped":3,"freezes":0,"frozen_ms":0,"keyframe_jumps":0,
 "reconnects":1,"disconnected_ms":7700,"watchdog":0,"target_ms":30,
 "audio":{"underruns":0,"waits":2,"drops":0,"lag_accept_ms":0}}
```

**字段**：

| 字段 | 区间 / 累计 | 含义 | 谁写 |
|---|---|---|---|
| `t` | — | 启动后的秒数 | 主线程 |
| `fps` | 区间 | 显示帧率 | 主线程 |
| `kbps` | 区间 | 读到的码率 | 读线程累加字节 |
| `lag_ms.p50/p95/p99` | 区间（汇总为全程） | 每显示一帧记一次"比最顺利情况晚多少"，5ms 一格的直方图；没样本时 -1 | 主线程 |
| `frames_shown` | 累计 | 显示帧数 | 主线程 |
| `frames_dropped` | 累计 | 追帧丢掉的视频帧（早丢 + 晚丢） | — |
| `freezes` / `frozen_ms` | 累计 | 损坏冻结次数 / 从坏帧到恢复的总时长 | 视频解码线程 |
| `keyframe_jumps` | 累计 | 积压跳关键帧次数 | 读线程 |
| `reconnects` / `disconnected_ms` | 累计 | 播放中断线后重连成功次数 / 断线到重连成功的总时长（不含首次连接重试） | 读线程 |
| `watchdog` | 累计 | 看门狗触发次数 | 读线程 |
| `target_ms` | 当前 | 目标延迟 | — |
| `audio.underruns` | 累计 | 正在出声时突然没数据 | 音频回调 |
| `audio.waits` | 累计 | 开始出声前等截止时间的次数 | 音频回调 |
| `audio.drops` | 累计 | 落后视频 0.5 秒以上被丢的音频帧 | 音频回调 |
| `audio.lag_accept_ms` | 当前 | 接受的音频滞后（见 3.3） | 音频回调 |

**实现**：[live_metrics.c](../src/live/live_metrics.c)。计数器由不同线程累加、主线程读出，只用于统计、不加锁（对齐的 64 位读写在 arm64 / x86-64 上不会撕裂，最多差一两次计数）。`-stats` 状态行同时新增 `au= aw= ad=`（音频三个计数）。

**测试校验**：每个场景都开 `-metrics_file`，检查文件非空，并核对：`tcp_restart` 重连 1 次、`blackout_300` 冻结 1 次且时长在 0~2 秒、`decoder_hang` 看门狗 ≥ 2、`tcp_give_up` 写出了汇总行、`clean` 帧率约 25。

## 5. 新增选项

| 选项 | 默认 | 作用 |
|---|---|---|
| `-audio_smooth` / `-noaudio_smooth` | 跟随 `-lowlatency` | 音频衔接 |
| `-metrics_file <路径>` | 不输出 | 运行指标 JSON 行文件 |
| `-metrics_interval <秒>` | 5 | 指标输出间隔 |

看门狗、抖动限幅、音频滞后接受没有单独开关，随 `-lowlatency` 启用。
